# Code Patterns — What Works in Toolblip

## Patterns Learned

### Next.js / React
- Use React Server Components for data fetching; use `'use client'` only when needed for interactivity
- Prefer Next.js App Router patterns over Pages Router for new features
- Use `next/navigation` (`useRouter`, `usePathname`) for routing, not `window.location`
- Form submissions: use server actions (`action=`) not client-side `fetch` to API routes
- Image optimization: use `next/image` component, not raw `<img>` tags

### API Design (Laravel / PHP Backend)
- All API endpoints return JSON with consistent envelope: `{ data, error, meta }`
- Use versioned routes: `/api/v1/`, `/api/v2/` — never break old versions without migration path
- Validate all inputs at controller level; don't rely on client-side validation alone
- Authentication: use Bearer token in `Authorization` header, validate on every protected route

### Database / Prisma
- Always use transactions for multi-step writes
- Soft deletes preferred over hard deletes for user-facing data
- Add indexes on foreign keys and frequently filtered columns early — don't wait for slow queries

### State Management
- Server state: prefer fetching in Server Components or server actions
- Client state: use React Context sparingly; Zustand/Recoil only for complex cross-component state
- URL state: prefer search params for filters/sort that should be shareable

### Performance
- Lazy-load components below the fold with `dynamic(..., { ssr: false })`
- Memoize expensive computations with `useMemo` / `React.memo`
- Batch API calls; avoid waterfall patterns in data fetching

### Error Handling
- Never swallow errors silently — always log and surface a user-friendly message
- Use custom error boundaries in React for graceful degradation
- API errors: return structured error responses, never raw exception traces

### Testing
- Unit test pure functions and utilities
- Integration test API routes with realistic request/response
- E2E test critical user flows (signup, purchase, login)
- Never leave `console.log` in production code
